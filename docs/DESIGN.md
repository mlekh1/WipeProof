## 1. Executive Summary & Problem Statement

When enterprise data centers, corporate IT departments, or government agencies retire, repurpose, or lease-return storage media, they face a critical security boundary: **data residual risk**. If sensitive data (PII, intellectual property, cryptographic keys, regulatory records) remains recoverable from retired media, severe legal, financial, and reputational breaches occur.

Existing solutions in the industry frequently suffer from:
1. **Unverifiable Paperwork:** Certificates are standard PDFs generated by arbitrary closed-source software with no cryptographic binding to the raw sanitize parameters or cryptographic signing identity.
2. **False Sanitization Claims (Overclaiming):** Labeling a sequential block overwrite (such as `dd if=/dev/zero`) on a Solid-State Drive (SSD) as "Purged" or "Sanitized", ignoring the Flash Translation Layer (FTL), wear leveling, overprovisioning, and retired blocks.
3. **Hidden Storage Blind Spots:** Failing to audit, detect, and unhide Host Protected Areas (HPA) and Device Configuration Overlays (DCO) on ATA storage.
4. **Firmware Placebo Blindness:** Trusting vendor-specific return codes without independent sampling, entropy verification, and hardware sanitize status confirmation.

**WipeProof** addresses these challenges through a Linux-first, cryptographically anchored disk sanitization engine that generates mathematically verifiable, tamper-evident wipe certificates adhering to NIST SP 800-88 Rev. 2 and IEEE 2883:2022.

| **Auditability & Code Clarity** | Highly readable, declarative logic. | **Cryptographic Ecosystem** | `cryptography` wraps OpenSSL 3.x (FIPS-capable, constant-time Ed25519 RFC 8032 implementation). | `ed25519-dalek` / `ring`. | Both provide constant-time, side-channel-resistant Ed25519. Python was chosen for rapid maintainability and rich ecosystem integration. |

## 3. Storage Media Capability Matrix & Standards Grounding

Sanitization claims must be rigorously grounded in physical media mechanics and official standards.

### Standards Grounding
* **NIST SP 800-88 Rev. 2 (Final, Sept 2025):** Focuses on decision trees and information governance, explicitly deferring storage-specific sanitization technical execution to **IEEE 2883:2022**.
* **IEEE 2883:2022 (Standard for Sanitizing Storage):** Defines explicit method requirements for magnetic (HDD), solid-state (NAND flash), and optical media across **Clear**, **Purge**, and **Destruct**.

### Capability Matrix

| Media Type | Hardware Interface | Sanitization Mechanism | IEEE 2883:2022 Technique | NIST 800-88 Rev. 2 Level | Limitations & Physics Boundary |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Rotational HDD** | SATA / IDE | Single-pass pseudorandom or zero overwrite | Overwrite | **Clear** | Overwrites all user-accessible LBAs. Does not erase defective sectors reallocated to G-List. |
| **Rotational HDD** | SATA / PATA | ATA Enhanced Secure Erase or ATA Sanitize Overwrite | Block Erase / Overwrite Sanitize | **Purge** | Erases user area, reallocated sectors, and metadata tracks. Requires firmware integrity. |
| **SATA SSD** | SATA (AHCI) | Sequential Overwrite (e.g. `dd`) | Overwrite (Logical only) | **Clear (AT BEST - NOT RECOMMENDED)** | **CRITICAL LIMITATION:** FTL wear leveling, spare overprovisioned flash blocks, and retired bad blocks remain unwritten. Overwrite cannot be claimed as Purge on flash. |
| **SATA SSD** | SATA (AHCI) | ATA Sanitize (`SANITIZE DEVICE` Block Erase / Crypto) | Block Erase / Cryptographic Erase | **Purge** | Native hardware block flash erase issued to controller. Purges all physical NAND blocks including overprovisioned pool. |
| **SATA SSD (Legacy)**| SATA (AHCI) | ATA Secure Erase (`SECURITY ERASE UNIT`) | Block Erase | **Purge** (with caveat) | Older drives had buggy firmware implementations. May fail silently or freeze drive if password handling is interrupted. |
| **NVMe SSD** | PCIe / NVMe | User Data Format (`Format NVM` User Data Erase = 1) | Format Erase | **Clear / Purge** (Dependent on controller scope) | Namespace-specific. May not purge persistent memory regions or retired blocks across multiple namespaces unless broadcast (NSID `0xFFFFFFFF`). |
| **NVMe SSD** | PCIe / NVMe | NVMe Sanitize (`Sanitize` Block Erase or Crypto Erase) | Block Erase / Cryptographic Erase | **Purge** | Controller-wide. Spans all namespaces, persistent memory, and overprovisioned/spare blocks. Uninterrupted across power cycles. |
| **Self-Encrypting Drive (SED)** | SATA / NVMe | Cryptographic Erase (Erasing MEK / Media Encryption Key) | Cryptographic Erase | **Purge** | Instantaneous. Requires certified AES hardware engine and proven, non-recoverable key generation/destruction. |
| **USB Flash / SD Card** | USB MSC / SD | Full Sequential Overwrite | Overwrite | **Clear** | Commodity USB microcontrollers lack standardized ATA/NVMe sanitize command sets. Wear-levelled blocks remain inaccessible. Cannot claim Purge. |

### STRIDE Assessment

| Threat Category | Specific Threat Scenario | Impact | WipeProof Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| **Spoofing** | Attacker creates a fake wipe certificate claiming a drive was purged. | Unauthorized disposal of un-wiped drives; regulatory penalties. | **Ed25519 Cryptographic Signatures (RFC 8032):** Every certificate is signed by an authenticated private key. Public key and Key ID are embedded; verifier checks mathematical signature validity. |
| **Tampering** | 1. Modifying certificate JSON (e.g. changing serial number or timestamp).<br>2. Tampering with PDF text while leaving signature.<br>3. Tampering with audit logs during execution. | Loss of integrity; mismatched audit records. | **RFC 8785 JSON Canonicalization Scheme (JCS):** Payload is canonicalized before hashing; any 1-byte change invalidates the signature.<br>**Cryptographic PDF Binding:** The canonical JSON hash is embedded in the PDF visual text, PDF metadata, and encoded in the verification QR code.<br>**In-memory log hashing:** Execution logs are SHA-256 hashed and included in the signed payload. |
| **Repudiation** | 1. Signing technician or facility claims "We never wiped or signed for that drive."<br>2. Verifier denies ever validating a cert. | Disputed legal liability during data breach investigations. | **Key Management & Hash Chaining:** Every certificate embeds the SHA-256 hash of the previous certificate produced by the station (`previous_certificate_hash`), forming a tamper-evident cryptographic chain. A missing or fabricated cert breaks chain continuity. |
| **Information Disclosure** | 1. Leakage of private signing key.<br>2. Residual data disclosure during sampling verification. | Key compromise allows rogue cert issuance; confidential data leaked in test output. | **Strict Key Handling:** Private keys stored with `0400` POSIX permissions; passphrases supported; clear design path for PKCS#11 / TPM 2.0 / YubiKey hardware tokens.<br>**Zero-Log Sampling:** Verification reads random sectors, calculates Shannon entropy and byte distributions, and immediately discards raw buffer data—never logging raw disk bytes. |
| **Denial of Service** | 1. Accidental wiping of host OS boot disk.<br>2. Drive bricking if sanitize is power-interrupted.<br>3. Resource exhaustion on public verification API. | Data loss on technician workstation; damaged hardware; verification service outage. | **Safety Interlocks:** Root disk / mountpoint detection halts engine if `/`, `/boot`, or swap is targeted. Mandatory interactive confirmation displaying Model, Serial, Capacity. Rate limiting and stateless signature verification on FastAPI endpoint. |
| **Elevation of Privilege** | Attacker exploits parser bugs in `wipeproof` running as root to gain root shell. | Host compromise on the wipe station. | **Principle of Least Privilege:** Separation between privileged low-level I/O runner and unprivileged certificate generator/verifier. Strict input validation on all CLI flags and device paths. |

## 5. What the Cryptographic Signature Proves (and Does NOT Prove)

### What the Signature PROVES:
1. **Cryptographic Authenticity:** The certificate was signed by an entity holding the private key associated with `key_id`.
2. **Payload Integrity:** The exact parameters recorded (serial number, method invoked, duration, sector count, sampling entropy results, tool git hash) have not been modified since signing.
3. **Audit Log Consistency:** The recorded command execution trace and tool exit codes are authentic to the signing session.
4. **Chronological Sequence:** The position of this wipe job in the hash chain relative to previous jobs.

### What the Signature DOES NOT PROVE (Explicit Limitations):
1. **Hardware Integrity / Firmware Placebo:** If the drive controller contains malicious, backdoored, or defective firmware that reports `ATA Command 0x11 (Sanitize) completed successfully` without pulsing erase voltages to flash cells, the software signature cannot detect this. The signature proves the software issued the command and received the success status.
2. **Host OS Authenticity (Unless Measured Boot is Used):** If the wipe environment itself is compromised (rootkit, tainted kernel), the tool cannot guarantee the integrity of device enumeration.
3. **Physical Custody & Label Swapping:** A signature cannot prove that physical drive serial label "SN12345" was not physically swapped onto another un-wiped drive casing.
4. **Post-Wipe State:** The signature proves the state of the drive at `timestamp_completed`. It does not prove the drive was not re-written after sanitization.

## 6. Safety Interlocks & Failsafe Design

1. **Boot and Mount Point Detection:**
   - Evaluates `/proc/mounts`, `findmnt`, and `sysfs`.
   - Traverses parent/child block device trees (e.g. `/dev/nvme0n1p2` -> `/dev/nvme0n1`).
   - If target device is associated with `/`, `/boot`, `/home`, or active swap, the engine **immediately terminates with exit code 77 (EBUSY)** before any disk handles are opened.
2. **Interactive Typed Challenge:**
   - Standard CLI requires the operator to type the exact drive serial number and target name:  
     `Type the target serial number [WD-WCC4N1234567] to confirm complete destruction:`
3. **Automated / Batch Guard:**
   - In non-interactive scripting mode, `--force-yes-i-understand-data-loss` AND `--target <exact_path>` must both be supplied.
4. **Safe Mock / Loopback Driver Isolation:**
   - Destructive testing suites are hard-coded to require virtual loopback devices (e.g. `losetup`) or in-memory sparse virtual files.
   - If a test attempts to execute against a real non-loopback device node, the test runner aborts instantly.

## 8. Phased Implementation Roadmap

* **Phase 1: Architecture, Standards & Mentorship Grounding (Current)**
  - Formalize [docs/DESIGN.md](file:///E:/WipeProof/docs/DESIGN.md) and [LEARNING.md](file:///E:/WipeProof/LEARNING.md).
  - Explicit user approval before implementation.
* **Phase 2: Core Wipe Engine on Loopback/Mock Backend**
  - Device discovery & profiles (`lsblk`, `sysfs`, loopback abstraction).
  - Safety interlocks (root/boot disk rejection, typed serial confirmation, `--dry-run`).
  - HPA/DCO audit state tracker.
  - Sanitization drivers: Sequential Overwrite (Clear), ATA/NVMe Sanitize drivers with mock/loopback simulation.
  - Post-wipe verifier: Shannon entropy calculation, pseudo-random LBA sampling, partition table zero-probe.
  - Audit logger with monotonic timestamps and SHA-256 execution hashing.
* **Phase 3: Cryptographic Certificate Engine & PDF Notary**
  - RFC 8785 JSON Canonicalization Scheme (JCS) engine.
  - RFC 8032 Ed25519 key management and signing notary.
  - Hash-chaining state manager (`previous_certificate_hash`).
  - PDF certificate generator with embedded QR code.
* **Phase 4: Independent Verifier**
  - Standalone offline CLI verifier requiring only public key.
  - FastAPI verification service with certificate validation, revocation checking, and tamper detection.
* **Phase 5: Minimal Web UI & Reproducible End-to-End Demo**
  - Local single-page web UI.
  - Reproducible demo script: sets up a virtual loopback disk, populates with high-entropy mock data, wipes it, verifies zero entropy, signs a certificate, verifies validity, tampers with 1 byte in the JSON, and confirms signature failure.
* **Phase 6: Quality, Security Hardening & CI**
  - Unit & property-based tests (`pytest`, `hypothesis`).
  - Negative security tests (tampered JSON, wrong key, revoked key, swapped PDF).
  - Static security analysis (Bandit/Semgrep), dependency audit (`pip-audit`), type checks (`mypy`), GitHub Actions.
* **Phase 7: Live ISO Architecture & Multi-OS Design Notes**
  - Debian live-build recipe.
  - Architecture note for Windows (VDS/BitLocker/Storage Spaces) and Android (FBE/UFS hardware RPMB/eMMC erase).
