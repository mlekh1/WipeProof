## 1. Why WipeProof? The Problem with Existing Tools

When servers, workstations, and laptops are retired, recycled, or returned from cloud leases, data residual risk is paramount. Existing industry and open-source sanitization tools frequently suffer from four critical security flaws:

1. **Unverifiable Paperwork:** Certificates are cosmetic PDFs generated by opaque software with zero mathematical binding to the raw sanitize parameters or cryptographic identity.
2. **False Sanitization Claims (Overclaiming):** Labeling a sequential block overwrite (`dd if=/dev/zero`) on a Solid-State Drive (SSD) as "Purged" or "Sanitized", completely ignoring the **Flash Translation Layer (FTL)**, wear leveling, overprovisioned blocks, and retired bad blocks.
3. **Hidden Storage Blind Spots:** Failing to audit, unhide, and log **Host Protected Areas (HPA)** and **Device Configuration Overlays (DCO)** on ATA storage.
4. **Firmware Placebo Blindness:** Blindly trusting vendor controller return codes without statistical read-back, Shannon entropy calculation, and partition boundary zero-probing.

**WipeProof** solves this by combining physical storage command orchestration (**ATA Sanitize**, **NVMe Sanitize**, and honest **Clear Overwrite**) with **RFC 8785 (JCS) deterministic canonicalization**, **RFC 8032 (Ed25519) digital signatures**, and an **append-only Merkle transparency log**.

## 3. Storage Media Capability Matrix (NIST & IEEE Grounding)

| Media Type | Interface | Sanitization Mechanism | IEEE 2883:2022 Technique | NIST 800-88 Rev. 2 Level | Physical Limitations & Honest Boundaries |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Rotational HDD** | SATA / PATA | 1-Pass Pseudorandom or Zero Overwrite | Overwrite | **Clear** | Overwrites all user-accessible LBAs. Does not erase reallocated bad sectors. |
| **Rotational HDD** | SATA / PATA | ATA Enhanced Secure Erase / Sanitize Overwrite | Block Erase / Overwrite Sanitize | **Purge** | Erases user area, reallocated sectors, and metadata tracks. |
| **SATA SSD** | SATA (AHCI) | Sequential Overwrite (`dd`) | Overwrite (Logical only) | **Clear (Not Recommended)** | **CRITICAL LIMITATION:** FTL wear leveling, spare overprovisioned flash blocks, and retired bad blocks remain unwritten. Overwrite cannot be claimed as Purge on flash. |
| **SATA SSD** | SATA (AHCI) | ATA Sanitize (`SANITIZE DEVICE` Block Erase) | Block Erase | **Purge** | Hardware block flash erase issued to controller. Erases all physical NAND blocks including overprovisioned pool. |
| **NVMe SSD** | PCIe / NVMe | `Format NVM` (User Data Erase = 1) | Format Erase | **Clear / Purge** | Namespace-scoped. May not purge persistent memory regions unless broadcast across all namespaces. |
| **NVMe SSD** | PCIe / NVMe | `NVMe Sanitize` (Block Erase = 2) | Block Erase | **Purge** | Controller-wide. Spans all namespaces, persistent memory, and overprovisioned flash. Persists across power cycles. |
| **Self-Encrypting Drive (SED)**| SATA / NVMe | Cryptographic Erase (Erasing MEK) | Cryptographic Erase | **Purge** | Instantaneous. Requires certified AES hardware engine and proven, non-recoverable key destruction. |
| **USB Flash / SD Card** | USB MSC / SD | Sequential Overwrite | Overwrite | **Clear** | Commodity USB microcontrollers lack standardized ATA/NVMe sanitize command sets. Wear-levelled blocks remain inaccessible. Cannot claim Purge. |

## 4. Defense-in-Depth Safety Architecture

Wiping is inherently destructive. WipeProof implements failsafe interlocks:
1. **Root / Boot Disk Interlock:** The engine traverses mount trees. If target device is associated with `/`, `/boot`, `/home`, or active swap, it **terminates immediately with exit code 77 (`EBUSY`)** before any write file descriptors are opened.
2. **Interactive Typed Challenge:** The operator must manually type the exact drive serial number and model string before write handles are initialized.
3. **Loopback Test Isolation:** Destructive test suites strictly enforce virtual loopback devices (`/dev/loopX`) or sparse image files. Targeting a physical disk during test mode causes an immediate safety abort.

## 6. CLI Usage

### Scan Storage Media
Inspect all attached storage devices with OS mount safety annotations:
```bash
wipeproof scan
```

### Inspect Hardware & HPA/DCO Status
```bash
wipeproof info /dev/sdb
```

### Execute Secure Sanitization
```bash
# Interactive mode (prompts for typed serial confirmation)
wipeproof wipe /dev/sdb --output-cert cert.json

# Non-interactive automated CI/Batch mode
wipeproof wipe /dev/sdb \
  --force-yes-i-understand-data-loss \
  --expected-serial S5Y2NJ0N123456X \
  --output-cert /var/log/wipeproof/sdb_cert.json

# Safe Dry-Run (simulates strategy without writing bytes)
wipeproof wipe /dev/sdb --dry-run
```

### Independent Offline Certificate Verification
Verify cryptographic authenticity, RFC 8785 canonical hash integrity, and revocation status:
```bash
wipeproof verify cert.json --public-key station_public_key.pem
```

## 9. What the Cryptographic Signature Proves (and Does NOT Prove)

A key tenet of honest security engineering is transparency regarding trust boundaries:

### What the Signature PROVES:
1. **Mathematical Authenticity:** The certificate was signed by an entity possessing the private key associated with `key_id`.
2. **Payload Integrity:** The exact parameters recorded (serial number, method invoked, duration, sector count, Shannon entropy, tool git hash) have not been modified by even a single bit since signing.
3. **Audit Log Consistency:** The execution trace SHA-256 hash is embedded in the signed payload.
4. **Chronological Sequence:** The position of this wipe job in the cryptographic hash chain (`previous_certificate_hash`).

### What the Signature DOES NOT PROVE (Explicit Limitations):
1. **Firmware Placebo Attack:** If a drive's internal microcontroller is backdoored or defective and returns `0x00 SUCCESS` for `SANITIZE DEVICE` without actually pulsing erase voltages to the physical flash cells, software cannot detect this at the bus level.
2. **Physical Custody & Label Swapping:** The signature proves the drive controller reported serial number $S$; it does not prove an adversary did not physically swap chassis labels.
3. **Host OS Authenticity:** If the host OS is compromised by a rootkit, hardware queries can be intercepted unless running in a measured-boot, hardware-attested environment.
